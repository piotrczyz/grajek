# Anonymous device registration for notifications — Implementation Plan

## Overview
Roadmap foundation F-02. A phone with Grajek can register anonymously for push
notifications. It sends only a random device id and its Web Push subscription,
with no name and no identifying data (ADR 0001, PRD NFR Prywatność). It can
also ask the server for one test notification to prove that delivery works.
The backend is a Firebase Cloud Function with Firestore, built and tested only
locally (unit tests plus the Emulator Suite). Linking billing (the Blaze plan)
and deploying are manual steps for the user. The change unlocks S-08
(reminders).

## Current State Analysis
- The app is a client-only React + Vite PWA. `vite.config.ts:16-56`: the
  service worker is generated by `vite-plugin-pwa` with `strategies:
  'generateSW'`. `vite.config.ts:53` says "No runtimeCaching: the app makes no
  requests to external origins". The SW is registered only in the production
  build (`src/main.tsx:13-15`).
- The on-device storage contract is `src/storage/`. `openDb()` derives the DB
  version from `migrations.length` (`src/storage/db.ts:20-33`). The migration
  list is append-only, and today it holds only an empty v1
  (`src/storage/migrations.ts:3-8,19-22`).
- The welcome screen is the whole UI (`src/App.tsx:3-27`). There is no
  routing.
- `firebase.json:1-6` configures only Hosting, with a catch-all
  `** → /index.html` rewrite. `.firebaserc` selects `grajek-app`. There is no
  `functions/` folder, no Firestore config and no emulator config.
- `.gitignore` already ignores `*.local` (covers `.secret.local` and
  `.env.local`) and `node_modules`.
- `context/foundation/tech-stack.md` (Data & Storage) named PostgreSQL for the
  F-02 server, with Firebase only as a note. The planning commit updates it in
  place: Firebase Functions + Firestore + Web Push (VAPID), plus the
  `functions/` commands.
- CI (`.github/workflows/ci.yml`) runs lint, typecheck, unit, build and e2e
  for the root package only. It does not deploy.
- Machine fact: there is no Java on the planning machine. The Firestore
  emulator needs a JDK (21 for current `firebase-tools`); the Functions and
  Hosting emulators do not. Node is 24 (`.nvmrc`).

## Desired End State
- `functions/` is a separate TypeScript package with its own pnpm lockfile. It
  exports one HTTPS function `api` in region `europe-central2`, reached
  same-origin through the Hosting rewrite `/api/**`. It serves:
  - `PUT /api/devices/{deviceId}` with body `{ subscription: { endpoint, keys: { p256dh, auth } } }`.
    This is an idempotent upsert. It returns `204`; `400` on invalid input.
  - `DELETE /api/devices/{deviceId}` returns `204`, whether or not the device
    exists.
  - `POST /api/devices/{deviceId}/test` sends one fixed Polish test
    notification to that device's stored subscription. It returns:
    - `202` when sent;
    - `404` for an unknown device;
    - `429` within the cooldown (60 s);
    - `410` when the push service reports the subscription gone (the doc is
      deleted).
- Firestore holds `devices/{deviceId}` = `{ subscription, createdAt,
  updatedAt, lastTestAt? }` and nothing else. `firestore.rules` denies all
  client reads and writes. Only the function (Admin SDK) touches the data.
- In the PWA, a "Powiadomienia" panel on the welcome screen:
  - enables notifications on a user tap (permission → `pushManager.subscribe`
    → `PUT`);
  - sends a test notification;
  - can turn notifications off;
  - shows a plain Polish hint when the browser cannot receive push (for
    example iOS Safari outside an installed PWA).

  The device id is a `crypto.randomUUID()` kept in a new IndexedDB `device`
  store (migration v2).
- The production service worker shows incoming pushes and focuses or opens the
  app on a notification tap.
- `pnpm --dir functions test` (unit, no emulator) passes on any machine.
  `pnpm --dir functions test:emulators` passes wherever a JDK 21 is present (CI
  installs one). It runs the function against the Functions + Firestore
  emulators under the offline demo project `demo-grajek`.
- The README documents
  local emulators, the VAPID key setup, and the manual billing/deploy steps.

### Key discoveries
- The migration list is append-only and the DB version equals its length
  (`src/storage/migrations.ts:3-8`, `src/storage/db.ts:27`). The parallel S-01
  run also appends a migration. Whoever merges second re-indexes their entry.
  Nothing is in the field yet, so this is safe.
- The SW is `generateSW` (`vite.config.ts:17`). Workbox's `importScripts`
  option adds a hand-written script to the generated SW without switching F-01
  to `injectManifest`.
- The Hosting catch-all rewrite (`firebase.json:5`) must stay last. The new
  `/api/**` function rewrite goes before it.
- The Functions emulator does not emulate push delivery. With Web Push
  (VAPID), sends are plain HTTPS POSTs to the push service and need no Google
  credential. This lets the test-send path run on the emulator with a fake
  sender, or against a real browser endpoint, without any console step
  (Consult).

## What we're NOT doing
- No reminder time, no per-day "practised" flag, no scheduling, no daily
  sending (S-07/S-08). No placeholder fields: Firestore is schemaless, and
  S-07/S-08 extend the doc.
- No FCM client SDK, no Firebase JS SDK in the PWA, no Firebase Auth (incl.
  Anonymous Auth), no App Check.
- No deploy, no `firebase deploy`, no cloud changes, no billing changes. No
  real `grajek-app` resources are created or touched by the agent.
- No `pushsubscriptionchange` re-registration inside the SW. A re-tap of
  "enable", or S-08, refreshes the subscription. It is noted as a follow-up.
- No server-side rate limiting beyond the per-device test cooldown and request
  validation.
- Nothing in the `szkielet-aplikacji-offline` change folder. No S-01 profile or
  instrument work.
- No legal/RODO text in the app. Parental consent is the user's open question
  (roadmap F-02 Unknowns) and blocks publication, not this build.

## Implementation Approach
**Server.** A standalone `functions/` package (TypeScript, Node 22 runtime,
`firebase-functions` v2 `onRequest`, `firebase-admin`, `web-push`). It has its
own `package.json` and `pnpm-lock.yaml`, so the root install and the root CI
steps stay unchanged and the folder deploys on its own.

The logic is split into pure, injected parts:
- `validation` (deviceId UUID, subscription shape, a push-endpoint host
  allowlist, so the function never POSTs to arbitrary URLs);
- a `DeviceRepository` interface with a Firestore implementation;
- a `PushSender` interface with a `web-push` implementation.

A small router maps method and path to handlers. Unit tests use in-memory
fakes, so the whole security boundary is tested without Java. An emulator
suite drives the real function and Firestore emulator through HTTP. Its push
sender is replaced by an env-selected recording sender
(`PUSH_SENDER=log`, honoured only when `FUNCTIONS_EMULATOR === 'true'`).

**Keys.** The VAPID key pair: the public key goes to the client as
`VITE_VAPID_PUBLIC_KEY` (build-time env) and to the server as a
`defineString` param. The private key is a `defineSecret`
(`VAPID_PRIVATE_KEY`), locally supplied by `functions/.secret.local`
(gitignored).

**Client.** `src/push/` holds:
- a device-id helper on the new IndexedDB `device` store;
- a small API client using `fetch` against `VITE_PUSH_API_BASE` (default
  `/api`);
- a `subscribe/unsubscribe` controller over `navigator.serviceWorker.ready`
  and `pushManager`.

`public/push-sw.js` (push + notificationclick handlers) is pulled into the
generated SW with `workbox.importScripts`. A Vite dev-server proxy maps `/api`
to the functions emulator.

**Alternatives rejected (Consult):**
- FCM web (adds the Firebase SDK and a second Google-issued installation id,
  and needs real credentials to send even from the emulator);
- direct client writes to Firestore under security rules (rules tests need the
  Java emulator, and the client would need the Firebase SDK);
- Anonymous Auth (another identifier);
- localStorage for the device id (the SW cannot read it, and it bypasses the
  storage contract).

One increment: the client is useless without the endpoint, and the endpoint
has no consumer without the client. The four phases fit rs-core §8.

## Critical Implementation Details
- **Rewrite order.** `firebase.json` `hosting.rewrites` must list
  `{ "source": "/api/**", "function": { "functionId": "api", "region": "europe-central2" } }`
  before `**`. The function strips the `/api` prefix itself, or matches both
  prefixed and unprefixed paths, so it works through the rewrite and when
  called directly on the emulator URL.
- **Emulators are offline-only.** Every emulator script passes
  `--project demo-grajek`. A `demo-` project id can never reach real cloud
  resources.
- **Stale subscriptions.** A `web-push` error with status 404 or 410 deletes
  `devices/{id}` and returns `410` to the client. The client then clears its
  local registration state.
- **Test cooldown.** `lastTestAt` is written on a successful send. A second
  test within 60 s returns `429` without sending.
- **Request limits.** Only `application/json` is accepted. Bodies over 4 KB
  are rejected. Any unknown field in the body is ignored and never stored.
- **iOS.** Web Push works only on iOS/iPadOS 16.4+ in a PWA added to the home
  screen. The panel detects missing `PushManager` / `Notification` and shows
  the install hint instead of the button. Permission is requested only inside
  the button's click handler (iOS requires a user gesture).
- **SW scope.** `public/push-sw.js` is plain JS (not bundled). It is
  precached by the existing glob, so it is also cached under `no-cache`
  semantics via the SW. `firebase.json` gets a `no-cache` header for
  `/push-sw.js` like `/sw.js`.

## Phase 1: Device registry function
### Overview
The backend contract, runnable and unit-tested without any emulator.

### Required changes
#### 1. Functions package
- **File**: `functions/package.json`, `functions/pnpm-lock.yaml`, `functions/tsconfig.json`, `functions/vitest.config.ts`, `functions/.gitignore`
- **Goal**: A self-contained TypeScript package for the Cloud Function. It uses
  its own lockfile and is independent of the root install.
- **Contract**:
  - `engines.node` `22`; `main` `lib/index.js`.
  - Dependencies: `firebase-functions`, `firebase-admin`, `web-push`.
  - Dev dependencies: `typescript`, `vitest`, `firebase-tools` (pinned,
    provides the `firebase` CLI for emulators), `@types/web-push`.
  - Scripts: `build` (tsc → `lib/`), `typecheck`, `test` (vitest unit),
    `test:emulators` (Phase 4), `emulators` (Phase 4).
  - `functions/.gitignore`: `lib/`, `.secret.local`.

#### 2. Validation and domain
- **File**: `functions/src/devices/validation.ts`, `functions/src/devices/types.ts`
- **Goal**: Reject anything that is not an anonymous registration. Never
  accept a push endpoint outside known push services.
- **Contract**:
  - `parseDeviceId(s): string | null`: lower-case UUID v4 only.
  - `parseSubscription(body): PushSubscriptionRecord | null`:
    - `endpoint` is an `https:` URL whose host matches the allowlist
      `fcm.googleapis.com`, `*.push.apple.com`,
      `updates.push.services.mozilla.com`, `*.notify.windows.com`;
    - `keys.p256dh` and `keys.auth` are non-empty base64url strings with
      length caps;
    - extra fields are dropped.
  - `DeviceRecord = { subscription, createdAt, updatedAt, lastTestAt? }`
    (timestamps as Firestore Timestamps / Date).

#### 3. Repository and sender
- **File**: `functions/src/devices/repository.ts`, `functions/src/devices/push-sender.ts`
- **Goal**: Isolate Firestore and Web Push behind interfaces so handlers are
  unit-testable.
- **Contract**:
  - `DeviceRepository { upsert(id, subscription, now), get(id), delete(id), markTested(id, now) }`.
    The Firestore implementation uses collection `devices`. `upsert` keeps
    `createdAt` on update.
  - `PushSender { send(subscription, payload): Promise<'sent' | 'gone'> }`.
    The `web-push` implementation uses the VAPID subject
    (`mailto:` from a param), the public param and the private secret. Push
    service status 404/410 → `'gone'`; anything else throws.
  - `createLogSender()` records calls (used only on the emulator, Phase 4).

#### 4. HTTP handler and entry point
- **File**: `functions/src/devices/handler.ts`, `functions/src/index.ts`
- **Goal**: The three endpoints from Desired End State, with the status codes,
  the cooldown and the stale-subscription cleanup.
- **Contract**:
  - `createDevicesHandler({ repo, sender, now, testCooldownMs = 60000 })`
    returns `(req, res)`.
  - Routes: `PUT|DELETE /devices/{id}`, `POST /devices/{id}/test`, each with
    or without the `/api` prefix.
  - Responses: `405` for other methods on known paths, `404` for unknown
    paths, JSON error body `{ error: <code> }`.
  - Test payload: JSON `{ title: "Grajek", body: <fixed encouraging Polish sentence>, tag: "grajek-test" }`.
  - `index.ts` exports `api = onRequest({ region: 'europe-central2', secrets: [VAPID_PRIVATE_KEY], cors: false, maxInstances: 2 }, handler)`.
    `firebase-admin` is initialised once. The sender is selected by
    `PUSH_SENDER=log` only when `FUNCTIONS_EMULATOR === 'true'`.

#### 5. Firebase project config
- **File**: `firebase.json`, `firestore.rules`, `firestore.indexes.json`
- **Goal**: Wire functions, Firestore and emulators into the existing project
  config without changing Hosting behaviour for the app shell.
- **Contract**:
  - `functions: [{ source: "functions", codebase: "default", runtime: "nodejs22", predeploy: ["pnpm --dir functions build"] }]`.
  - `firestore: { rules, indexes }`.
  - `emulators: { functions: 5001, firestore: 8080, hosting: 5000, ui: { enabled: false }, singleProjectMode: true }`.
  - Hosting: the `/api/**` → function `api` rewrite before `**`, plus a
    `no-cache` header for `/push-sw.js`.
  - `firestore.rules`: `allow read, write: if false` for every path.
    `firestore.indexes.json` is empty.

#### 6. Lint wiring
- **File**: `eslint.config.js`
- **Goal**: The root lint covers `functions/src` with Node globals and ignores
  `functions/lib`.
- **Contract**: `globalIgnores` adds `functions/lib`; a block for
  `functions/**/*.ts` sets `globals.node`.

### Success criteria
#### Automated
- `pnpm --dir functions install --frozen-lockfile && pnpm --dir functions build` succeeds
- `pnpm --dir functions typecheck` passes
- `pnpm --dir functions test` passes, covering:
  - register upsert keeps `createdAt`;
  - invalid id/body → 400;
  - non-allowlisted endpoint → 400;
  - delete is idempotent;
  - test-send 202 / 404 / 429 cooldown / 410 with doc deleted;
  - stored record has no fields beyond `subscription`, `createdAt`,

- `pnpm lint` passes with `functions/src` linted
- `firebase.json` lists the `/api/**` rewrite before `**` and `firestore.rules` denies all (checked by a unit test that reads both files)

## Phase 2: Client registration module
### Overview
The PWA side of the contract, without UI: anonymous id, subscription, API calls
and the SW push handler.

### Required changes
#### 1. Device store migration
- **File**: `src/storage/migrations.ts`, `src/storage/db.test.ts`
- **Goal**: Persist the anonymous device id and registration state on the
  device, following the append-only contract.
- **Contract**:
  - Append migration v2 "device": creates object store `device` (out-of-line
    keys). The record lives under key `registration`:
    `{ deviceId: string, registered: boolean, endpoint?: string, updatedAt: number }`.
  - The existing v1 entry stays untouched.
  - The test asserts DB version 2 and the store's existence after upgrade
    from v1 and from empty.

#### 2. Push module
- **File**: `src/push/device-id.ts`, `src/push/api.ts`, `src/push/push.ts`, `src/push/index.ts`, `src/push/*.test.ts`
- **Goal**: One small API the UI (and later S-08) calls.
- **Contract**:
  - `getOrCreateDeviceId()`: reads or creates a `crypto.randomUUID()` in the
    `device` store.
  - `pushSupport(): 'supported' | 'needs-install' | 'unsupported' | 'denied'`:
    `'needs-install'` when on iOS without standalone display mode, or when
    `PushManager` is missing.
  - `enableNotifications()`: request permission (must be called from a user
    gesture), then `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: VITE_VAPID_PUBLIC_KEY })`,
    then `PUT {base}/devices/{id}`, then store `registered: true`.
  - `disableNotifications()`: `DELETE`, then `subscription.unsubscribe()`,
    then `registered: false`.
  - `sendTestNotification(): 'sent' | 'cooldown' | 'gone' | 'error'`. On
    `'gone'`, clear local state.
  - `getRegistrationState()`.
  - The API base is `import.meta.env.VITE_PUSH_API_BASE ?? '/api'`. With no
    VAPID key configured, `pushSupport()` returns `'unsupported'`.
  - Typed `ImportMetaEnv` entries go in `src/vite-env.d.ts`.

#### 3. Service worker push handler
- **File**: `public/push-sw.js`, `vite.config.ts`
- **Goal**: Show pushes when the app is closed. Open or focus the app on tap.
- **Contract**:
  - The `push` handler parses the JSON payload `{ title, body, tag }` and
    calls `self.registration.showNotification` with the app icon. It falls
    back to the title "Grajek" on a missing or invalid payload.
  - The `notificationclick` handler closes the notification, then focuses an
    existing client or opens the scope URL.
  - `vite.config.ts`: `workbox.importScripts: ['push-sw.js']`, plus
    `server.proxy['/api']` → `http://127.0.0.1:5001/demo-grajek/europe-central2/api`.
  - Keep the existing comment intent and update the "no external origins"
    comment to say that push endpoints are called only by the browser's push
    service.

## Testing Strategy
- **Functions unit (Vitest, `functions/`)**: validation, handler routing,
  status codes, cooldown, stale-subscription cleanup and the stored-field
  whitelist, all with in-memory `DeviceRepository` and `PushSender` fakes. It
  runs anywhere and is the primary proof of the security boundary.
- **Functions integration (Emulator Suite)**: the real HTTP function with the
  Firestore emulator under `demo-grajek`, and a recording push sender. It
  needs JDK 21. CI runs it.
- **Client unit (Vitest + jsdom + fake-indexeddb)**: migration v2, device id,
  push controller with mocked browser APIs, and panel states.
- **E2E (Playwright, mobile Chromium)**: the panel renders in the production
  build, and the SW imports the push handler. Real push delivery is not
  automatable (no push service in headless CI).
- **Manual**: real-device delivery on Android and iOS after the user deploys.

## Migration Notes
- IndexedDB v1 → v2 adds an empty `device` store. Rollback: the store is
  additive, and older code ignores it. Shipping a build without v2 after v2
  ran is not possible with IndexedDB (no version downgrade), which is the
  existing F-01 contract. Nothing is in the field yet.
- Firestore: a new collection only. Rollback = delete the `devices`
  collection. There is no data migration.
- If S-01 merges its own migration first, F-02's migration is re-appended
